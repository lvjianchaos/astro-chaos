### 多益网络

#### Q1 自我介绍

吕建超，武汉理工大学计算机科学与技术专业，2027 届。没有实习经历，时间都放在两个从 0 到 1 的项目上：一个是分布式短链服务，一个是企业级 RAG 问答服务。

两个项目刻意挑了不同的难点：短链磨的是高并发只读链路下的正确性和一致性；RAGent 磨的是检索精度和多模型调用的稳定性。技术栈 Java + Spring Boot/Spring Cloud Alibaba，中间件 MySQL、Redis、Milvus，消息用 Redis Stream 和 MQ。方向是后端，想在并发链路和稳定性上继续深入。

#### Q2 最满意的项目 + 最大的挑战

最满意 RAGent。最初的实现是最常见的「全库向量化 + topK + rerank」，问题在于企业知识库不是一个库，HR、产品、售后各是一个 collection，语义相近但业务无关的内容会被混在一起捞上来，而 rerank 只能重排候选，候选错了它救不回来。

改法是先缩小范围再检索：

1. 建意图树，知识库类意图节点绑定 collection，问题先过意图识别，得到命中的节点和置信度；
2. 只在这些节点指向的库里定向检索，TopK 乘一个系数做补偿；
3. 全局向量检索降级成条件触发的兜底通道：意图通道关闭、没有意图、最高分低于 0.6、或只有一个意图且分数低于 0.8 时才启动；
4. 后置链先去重再 rerank，省一次模型调用。

放弃的方案：微调 embedding 模型（没有标注数据，迭代以周计）；纯 BM25（对同义表达无能为力）。

代价也说清楚：意图树是业务知识的映射，业务变了树得跟着改；意图识别多一次模型调用；最怕的是误判导致漏召回，所以用 0.4/0.6/0.8 三级阈值加兜底通道缓解。验证上只是自己构造了一批覆盖各知识库的 query 做离线对比，没有线上流量，这点不能吹。

如果问技术更硬的挑战，说短链的分片键：`t_link` 按 gid 分 16 片，但跳转时手里只有短码，按 gid 分片要么 16 片广播、要么全表找 gid。所以加了一张窄表 `t_link_goto`，只存 `full_short_url -> gid`，并且按 `full_short_url` 自己分片，把定位分片变成一次单片点查，代价是多一次查询，读侧用缓存挡掉。

#### Q3 更喜欢存量项目还是新项目

更愿意在存量项目上做，但要能读懂它。

三个理由：存量项目是真实工作的主战场，我 RAGent 就是在别人的代码库上做的二次开发，先花时间把检索链路每个类的职责画出来才敢动；存量项目逼你做约束下的设计，已有接口不能破、已有数据要迁、调用方不能感知，这三件事才是真考场，我加通道时就要求单通道异常必须降级成空结果而不是抛出去；存量项目收益可度量，有基线有对比，新项目很容易做完没人用。

0 到 1 的价值也承认：决策密度高，选型、分层、表结构都得自己定，我短链就是这么来的，最大的收获是每个选择都得自己负责。

#### Q4 Git 协作与冲突处理

解冲突分五步：

1. 先 `fetch` 再在本地 merge/rebase，让冲突在自己机器上炸，而不是在合并那一刻；
2. `git status` 看清范围，区分同行冲突和结构性冲突（文件被删、签名被改）；
3. 逐文件按语义合并。冲突标记只说明两块文本撞了，正确解经常是两边都要，比如他改签名、我加参数，正确解是合起来。盲目保一边最容易引 bug；
4. 解完要验证：编译、跑测试、起服务看一眼。Git 只保证文本不冲突，语义冲突它不管；
5. `git add` 后 `--continue`，推之前再看一眼 `git diff`。

减少冲突靠习惯：分支小、活短、每天先 pull、一个 PR 只做一件事、格式化改动不和逻辑改动放同一个提交。

几个常被追问的点：`merge` 保留分支历史并产生合并提交，`rebase` 把提交重放到目标分支之后，历史是直线但哈希会变，公共分支不要 rebase。`reset` 移动指针会改写历史，`revert` 生成反向提交不改历史，已经推到远端的只能用 `revert`。误提交密码先轮换凭据，再清洗历史，光删文件没用。

#### Q6 AI 参与开发

**工作流**分四段，原则是人负责决策和验收，AI 负责产出。

1. 对齐需求：不让它直接写代码，先让它反问我边界条件、失败处理、幂等、数据量级，产出一份结构化的需求与约束清单。经常在这一步发现自己需求没想清楚。
2. 定方案：要 2-3 个方案并说明代价，我再选。不能让它直接给「最佳实践」，它的默认倾向是教科书方案，忽略我项目的存量约束。
3. 小步实现：一次只改一个文件或一个方法，每次读完 diff。审查重点不是语法，是异常路径有没有覆盖、有没有引入新的共享可变状态、有没有动我已有的接口。
4. 验证：先让它写测试和验收用例再实现，跑通后自己构造边界输入（空集合、超大值、并发）再打一遍。

两条硬规矩：密钥、连接串、用户数据不进上下文；AI 给的 API 一律回官方文档核实，它编 API 的概率比编逻辑高。

**对我的影响**是分层的。被压缩的是翻译型工作：DTO 转换、样板 CRUD、单测脚手架、SQL 初稿、文档。被放大的是判断型工作：需求边界、数据一致性、并发正确性、性能成本。还多了一类工作叫验收——生成量远大于能细读的量，只能靠测试、类型、断言、可观测兜底，反而让我比以前更重视工程质量。所以准确说法是把时间从敲挪到了想和验，关键路径的代码还是自己写自己读。

**对后端的未来影响**，三个判断：

1. 写代码本身会快速贬值，对系统行为负责会升值。AI 能写出编译通过的代码，但它不知道这条 SQL 在 1 亿行上会全表扫、不知道删缓存放在事务里会有脏读窗口、不知道这个重试会放大成雪崩。
2. 重心往两端移：往上领域建模和业务约束，往下数据、并发、可观测性和成本。中间那层把需求翻译成 CRUD 的会被吃得最多。成本是新出现的一块，以前优化 QPS，现在还要优化 token 和延迟，这已经是后端问题（我 RAGent 里做降级链、首包探测本质就是可用性和成本工程）。
3. AI 应用会变成后端的标准子系统，就像现在没人觉得接数据库是特殊技能。那时候稀缺的不是会调模型 API，而是会做召回质量、多模型容灾、流式稳定性。

一句话：AI 让实现变便宜，让判断变贵。

#### Q9 MySQL 事务与 ACID

事务是一组要么全成功要么全失败的 SQL。ACID 四个保证不是靠同一个机制实现的，这是最容易答漏的地方。

| 特性 | 机制 | 说明 |
| --- | --- | --- |
| 原子性 A | undo log | 执行增删改前先记「怎么撤销」，回滚时反向执行。它是逻辑日志，记反向操作而不是数据页镜像 |
| 持久性 D | redo log + WAL | 先顺序写日志并刷盘，数据页可以延迟刷。顺序写快过随机写。`innodb_flush_log_at_trx_commit=1` 每次提交 fsync，0 每秒刷，2 交给 OS |
| 隔离性 I | 锁 + MVCC | 写写靠行锁排队，读写靠 MVCC。MVCC 是隐藏字段（`DB_TRX_ID`、`DB_ROLL_PTR`）+ undo 版本链 + Read View |
| 一致性 C | 约束 + A/I/D + 应用层 | 它不是某个日志的产物，而是前三个特性的目的。数据库负责约束（唯一索引、主键、外键、CHECK），业务规则靠代码 |

MVCC 的可见性判断：拿 Read View 的 `m_ids`、`min_trx_id`、`max_trx_id` 去判断版本链上哪个版本可见，不可见就顺 `DB_ROLL_PTR` 往下找。RC 每条 SELECT 新建 Read View，RR 只在第一次快照读建一次，这就是 RC 会不可重复读、RR 不会的根源。

幻读要单独说：普通快照读靠 MVCC 看不到别人新插入，但当前读（`FOR UPDATE`、UPDATE、DELETE）读最新版本，所以要靠 Next-Key Lock（记录锁 + 间隙锁）挡插入。而且 RR 下先普通 SELECT、别人插入提交、自己去 UPDATE（当前读能看到它），更新后 `trx_id` 变成自己的，再 SELECT 就看见了，这是 RR 下的幻读。所以不能说 RR 彻底解决了幻读。

补一个必答项：redo 在 InnoDB 层、binlog 在 Server 层，两份日志必须一致，所以用两阶段提交：写 redo（prepare）→ 写 binlog → 写 redo（commit）。崩溃恢复以 binlog 是否完整为判据。

落到项目：`@Transactional` 都显式写了 `rollbackFor = Exception.class`，因为默认只回滚 `RuntimeException` 和 `Error`，检查异常不回滚。另外短码唯一性没押在事务上——并发创建时「先查后插」在 RR 下也挡不住，靠的是唯一索引 `(full_short_url, del_time)` 加捕获 `DuplicateKeyException`。事务保证原子性，「唯一」必须交给数据库约束。

#### Q10 并发与并行

一句话：并发是结构，并行是执行。

并发是系统具备同时处理多个任务的能力，描述任务怎么被组织，单核也能并发，靠时间片轮转，宏观像同时微观是交替，目的是提高吞吐、掩盖等待。并行是物理上同一时刻执行，需要多核，目的是缩短单任务耗时，所以只有能吃满 CPU 的任务才划算。并行是并发的一种实现方式。

代价不同：并发付出的上下文切换（寄存器、缓存失效、TLB 抖动），所以线程不是越多越好；并行的上限是 Amdahl 定律，串行部分占 10%，堆到 100 核也只能快 10 倍。

回扣项目：RAGent 的多通道并行检索本质是并发不是并行，每个通道都在等 IO，CPU 基本空转，所以线程能开到 `CPU*4`；文档解析分块是 CPU 密集，就用少量线程加有界队列。Redis 也是并发但不并行，单线程执行命令，靠 IO 多路复用把等待重叠起来，没有锁竞争恰好是它快的原因。

#### Q11 深拷贝与浅拷贝

浅拷贝只复制最外层对象，引用字段还是同一个堆对象；深拷贝会把引用指向的对象也复制一份。拷贝后浅拷贝 `A.list == B.list`，深拷贝不等。

Java 里：`Object.clone()` 默认是浅拷贝，按字段做按位复制；要深拷得在 `clone()` 里递归或者走序列化。`Cloneable` 是标记接口，不实现调 `clone()` 会抛 `CloneNotSupportedException`。数组的 `clone()` 也是浅拷贝。

深拷贝常见三种实现：手动递归或拷贝构造器（最可控最快，代码啰嗦）、序列化反序列化（省代码，性能差，要处理循环引用、`transient` 会丢）、拷贝构造器加 Builder。

三个坑：`String` 和包装类不可变，看起来像深拷贝，但 `Date`、集合、数组都是可变的，这些才需要真拷；`BeanUtils.copyProperties`、Hutool 的 `BeanUtil.toBean` 都是浅拷贝，很多人以为它做了深拷贝，结果 DTO 和 DO 共享同一个集合；循环引用会让递归和序列化爆栈。

实践上优先考虑不可变对象（`final` 字段、不暴露集合、用 `record`），不可变就不用拷，比写深拷贝省事也安全。

项目里 DO 到 DTO 用的就是 `BeanUtil.toBean`，浅拷贝，没出问题是因为 DTO 只读组装、不往回写，DO 里也没有把可变集合暴露出去。哪天 DTO 需要改集合里的元素，就必须换成深拷贝，否则会污染别处的数据。

#### Q12 线程的一些操作

创建方式四种：继承 `Thread`、实现 `Runnable`、实现 `Callable` 配 `Future`（有返回值和异常）、线程池。生产上只用线程池。

六种状态：NEW、RUNNABLE、BLOCKED（等 synchronized 监视器锁）、WAITING（`wait`/`join`/`park` 无超时）、TIMED_WAITING（带时间）、TERMINATED。注意 BLOCKED 特指等锁，等 IO 的线程在 JVM 看来是 RUNNABLE。

常用 API：`start`/`run`（`start` 才开新线程，直接调 `run` 是普通方法）、`join`/`sleep`/`yield`、`interrupt`/`isInterrupted`、`setDaemon`、`setPriority`，线程间协作的 `wait`/`notify`（必须在 synchronized 里，`wait` 释放锁、`sleep` 不释放）、`LockSupport.park`/`unpark`。

停止线程的正确方式是 `interrupt` 加标志位，不是 `stop`。`interrupt` 只是设标志位，线程在 `sleep`/`wait`/`join` 时会抛 `InterruptedException` 并清标志，所以捕获后要 `Thread.currentThread().interrupt()` 恢复，否则上层感知不到。

项目里除了线程池还用了 `CompletableFuture` 做并行编排（多通道检索、记忆加载），以及在池外再套一层 `TtlExecutors`，把 `ThreadLocal` 里的用户上下文和 traceId 传到池内线程，不然日志里的链路 ID 就断在异步边界上了。

#### Q13 线程池参数与拒绝策略

七个参数：核心线程数、最大线程数、空闲存活时间、时间单位、工作队列、线程工厂、拒绝策略。

提交顺序：核心线程没满就直接开线程；核心满了进队列；队列满了开到最大线程数；最大也满了走拒绝策略。反直觉的点是 `LinkedBlockingQueue` 不设容量就是无界队列，第三步永远到不了，`maxPoolSize` 形同虚设，任务无限堆积到延迟爆炸或 OOM。所以队列必须有界。

拒绝策略四种：`AbortPolicy`（默认，抛异常，快速失败）、`CallerRunsPolicy`（提交任务的线程自己跑，形成背压，代价是提交线程被占住）、`DiscardPolicy`（静默丢弃）、`DiscardOldestPolicy`（丢队列里最老的，再提交新的）。选法看两条：任务丢了有没有业务影响，调用方能不能接受变慢。绝对不能接受的是既不报错又悄悄丢。

RAGent 里按业务隔离了 10 个线程池，不用公共池，一个慢依赖不该拖死整条链路。几个关键的：

| 线程池 | core/max | 队列 | 拒绝策略 | 原因 |
| --- | --- | --- | --- | --- |
| `ragRetrievalExecutor`（通道并行检索） | `CPU*4` / `CPU*4` | `SynchronousQueue` | `CallerRuns` | 纯 IO 等待，CPU 空转，线程可以多开；交接队列不排队，满了立刻背压，不无界堆积 |
| `intentClassifyExecutor`（意图识别） | `CPU` / `CPU*2` | `SynchronousQueue` | `CallerRuns` | 单次调用带超时，不需要大池 |
| `modelStreamExecutor`（流式输出） | `max(2,CPU/2)` / `max(4,CPU)` | `LinkedBlockingQueue(200)` | `Abort` | 流式会话是长任务，入口已经有限流，池满就快速失败让上游返回排队中 |
| `chatEntryExecutor`（SSE 入口） | `= globalMaxConcurrent` | `SynchronousQueue` | `Abort` | 池大小直接等于承诺的并发上限，还开了 `allowCoreThreadTimeOut(true)` |
| `innerRetrievalExecutor`（库内检索） | `CPU*2` / `CPU*4` | `LinkedBlockingQueue(100)` | `CallerRuns` | 被外层再拆一层，总量会放大，必须有界队列兜住 |

参数怎么定：先看任务性质，IO 密集用 `核数 × (1 + 等待/计算)`，CPU 密集约等于核数；再看总量的上界在哪，一个请求最多并发 3-5 个通道，入口被限流卡在 `globalMaxConcurrent`，池内任务数上界是可算的，这才敢开 `CPU*4`；最后用队列和拒绝策略定义满了怎么办，这一步比数字重要。

两个工程细节：线程命名前缀，`jstack` 里一眼看出是哪个池卡住，`pool-1-thread-3` 最难查；`TtlExecutors` 做上下文透传。

另外读代码发现一个自己的问题：短链 Redis Stream 消费者池是 `core=max=1` + `SynchronousQueue` + `DiscardOldestPolicy`，但交接队列里没有「老任务」可丢，`poll()` 返回 null，实际会退化成抛 `RejectedExecutionException`，高峰期可能丢统计消息。应该改 `CallerRunsPolicy`，或者干脆单线程循环消费。

#### Q14 Redis 常见问题

分四类：读的问题（穿透/击穿/雪崩）、一致性、容量（大 key、热 key、内存）、分布式锁和原子性。

**穿透**：key 在缓存和库里都不存在，每次都打 DB。我布隆过滤器和空值缓存两个都用。布隆 `tryInit(1 亿, 0.001)`，算下来约 14.4 bit/元素、约 180MB、k≈10 个哈希函数；空值缓存写占位值 `-`，TTL 30 分钟，挡布隆误判。布隆的代价要说清楚：只误判「存在」不误判「不存在」，所以能挡穿透；不支持删除，所以删场景不能拿它当判断依据；超过预估容量误判率会飙升。

**击穿**：单个热点 key 过期瞬间大量请求同时查库。做法是锁加双重检查，按短码粒度加 Redisson `tryLock(100ms)`，抢到锁的再查一次缓存再查库再回填；没抢到的不等锁，直接再读一次缓存，读不到就 404。原因很简单，跳转是超高频只读链路，等锁比少一次命中更贵，堆在锁上会把 Tomcat 线程池占满。代价是极少数请求短暂 404，下一次就恢复了。

**雪崩**：大批 key 同时失效或 Redis 整体不可用。三层：过期时间打散（短链缓存的 TTL 按每条链接自己的剩余有效期算，天然分散）；降级要想清楚放行还是拦截，我的读链路选择查库而不是直接 404，同时必须有熔断防打穿 DB；高可用上主从加哨兵或 Cluster，别单点。

**一致性**：旁路缓存，读没命中查库回填，写先更新 DB 再删缓存。删而不是改，因为并发下更新缓存会被旧值覆盖，删除是幂等的。先更库再删，避免删完缓存、库还没更新的窗口里被回填旧值。这段还有窗口，见 Q16。

另外几个真实落点：ZSET 加 Lua 做分布式公平限流，必须用 Lua 保证读-判断-写原子，否则两个实例会拿到同一个名额；Pub/Sub 做跨实例的流式任务取消，它不持久化也不保证送达，所以配 `RBucket`（30 分钟 TTL）做双保险，Pub/Sub 只当快速通知；`SETNX` 做幂等，见 Q17。

#### Q15 Redis 内存超限

我自己跑的时候没遇到过，数据量很小。但有两件事当时就意识到了：docker-compose 里 Redis 只设了密码，没设 `maxmemory`，默认到机器内存上限就是写失败或者被 OS kill；另外布隆过滤器本身约 180MB，是内存大户。

真打满了怎么定位：先 `INFO memory` 看 `used_memory`、`mem_fragmentation_ratio`（大于 1.5 说明碎片多），`INFO stats` 看 `evicted_keys`（大于 0 说明已经在悄悄淘汰了，是隐性数据丢失）；再 `redis-cli --bigkeys` 找大 key，`MEMORY USAGE key` 单点看，`slowlog` 看有没有大 key 操作；最后看趋势，是总量一直涨（漏 TTL、没有淘汰）还是尖峰（批量写入）。

解决顺序是从便宜到贵。先保证可淘汰：设 `maxmemory` 加策略，热数据要留就 `allkeys-lru` 或 `allkeys-lfu`，所有 key 都有 TTL 时用 `volatile-*` 更安全，注意 `volatile-lru` 在 key 都没 TTL 时会一个都淘汰不掉直接 OOM，默认的 `noeviction` 是写失败，对缓存一般不可接受。再降内存：强制 TTL、压缩 value、拆大 key、布隆按实际量级给容量。然后加容量：主从解决读，Cluster 解决内存和写，但多 key 操作要同 slot。最后别把 Redis 当数据库，统计明细是 Redis Stream 异步落库，Redis 只做缓冲和去重标记。

#### Q16 短链项目怎么保证数据一致性

分五层看，从下到上。

**第一层短码唯一**：并发创建时先查再插本身有竞态，正确性押在唯一索引上，`t_link` 是 `UNIQUE KEY (full_short_url, del_time)`，插入冲突就捕获 `DuplicateKeyException`，把短码补进布隆再抛异常让上层重试。`del_time` 参与唯一索引是有意的，软删除时写时间戳，已删记录不再占唯一键，短码可以复用，否则空间会被软删记录永久消耗。能用数据库约束保证的，不用应用层先查后插。

**第二层缓存与 DB**：读路径是缓存 → 布隆 → 空值缓存 → 加锁 → 查表 → 回填；写路径先更库再删缓存。这里有个我回头要改的隐患：删缓存和写库在同一个 `@Transactional` 方法里，也就是删缓存的时刻事务还没提交，中间有读请求会读到已提交的旧值并回填，事务提交完缓存就一直是旧值了。正确做法三种：挪到 `TransactionSynchronization#afterCommit`、延迟双删（提交后再删一次，间隔不小于一次读的耗时）、或者用 Canal 订阅 binlog 异步删缓存，业务代码完全不碰缓存。

**第三层跨分片**：`t_link` 按 gid 分 16 片，`t_link_goto` 按 `full_short_url` 分 16 片，一次创建是跨数据源写，ShardingSphere-JDBC 的本地事务只覆盖单数据源。处理方式不是追求强一致，而是让不一致无害：先插 `t_link` 再插 `t_link_goto`，跳转必须先命中 `t_link_goto` 才能定位 gid，没有 goto 记录就等于这条链接不存在，表现是 404 而不是错误跳转。所以分片键的选择其实决定了一致性边界。跨 gid 迁移用 Redisson 读写锁按短码串行化，一个事务里完成旧 gid 软删、新 gid 插入、goto 表更新，统计消费走读锁，避免读到迁移中间态。

**第四层统计异步**：跳转写 Redis Stream，消费者批量拉（batchSize 10、pollTimeout 3s）落库，见 Q17。落库用 `INSERT ... ON DUPLICATE KEY UPDATE pv = pv + 1`（唯一键 `(full_short_url, date, hour)`），累加本身不幂等，所以必须靠幂等键保证只累加一次。极端情况比如 Redis 挂了会把幂等键挤掉，导致重复计数，所以我把 PV/UV 定位成分析指标而不是账务数据，这个定位决定了我能接受多大误差。

**第五层主从**：异步复制有延迟，刚创建就读要走主库。我的短链创建完立刻回填缓存，写后读走缓存就不碰从库了。

#### Q17 消息只消费一次

短链跳转统计就是这个场景。跳转时把统计记录写进 Redis Stream（topic `short-link:stats-stream`，group `only-group`），消费者落库。异步就必然可能重复投递，所以做幂等，而且用的是两态不是简单的「处理过吗」：

- `setIfAbsent("short-link:idempotent:" + messageId, "0", 2min)`，抢到说明我是第一个处理者，状态是「处理中」；
- 消费完成后置 `"1"` 表示「已完成」，并显式删掉 Stream 里这条消息；
- 再收到同一条：是 `"1"` 就直接返回跳过；是 `"0"` 说明上次处理到一半挂了，抛异常让队列重试，这才是「至少一次」的正确实现；
- 消费抛异常时主动删掉幂等键，否则 2 分钟内这条消息永远重试不了。

为什么不能只用 SETNX 一次了事：只记「处理过」的话，第一次处理到一半宕机，键还在，消息重试就被误判成已处理直接丢，等于丢数据。所以必须有「处理中」和「已完成」两个状态。

通用套路也可以说一下：唯一业务键加去重表（或 Redis 去重）、状态机做前置条件判断（`update ... where status = 待处理`，靠影响行数判断谁抢到）、数据库唯一索引兜底。本质都是把幂等性从消息中间件挪到业务侧。

#### Q18 设计一个消息队列

先定目标和假设：高吞吐、多生产者多消费者、消息不丢、允许消费组内并行。整体分四块：存储、写入、消费、可靠性。

**存储模型**：单个 broker 上一个 topic 分成若干 partition，每个 partition 是一条只追加的日志文件，按段（segment）切分，段满就新建，段内顺序写。每条消息有递增的 offset。索引用稀疏索引：先按 offset 二分定位段，再读段内索引找到最近的文件位置，顺序扫描一小段。之所以这样设计，是因为只追加写是顺序 IO，机械盘和 SSD 上都比随机写快得多，而且读可以走页缓存和 `sendfile` 零拷贝，不经过用户态。

**写入路径**：生产者选分区（指定 key 哈希保证同 key 有序，或不指定轮询），发给该 partition 的 leader；leader 先写本地日志（可选 `mmap` 或 `FileChannel`），按配置决定同步刷盘还是异步刷盘；同步副本确认后返回成功。批量加压缩（`batch.size`、`linger.ms`）是为了摊薄网络和磁盘开销。

**消费模型**：消费组，一个 partition 同一时刻只分配给组内一个消费者，所以「组内并行度上限等于 partition 数」。用拉模式而不是推，消费者自己控制速率，天然形成背压，避免被推爆。位点（offset）由消费者提交到 broker 的位点 topic，区分自动提交和手动提交，手动提交才能实现「处理成功再提交」。

**投递语义**：至少一次（处理完再提交位点，重复靠幂等键去重）、至多一次（先提交再处理）、精确一次（事务或幂等生产者加事务性消费，代价最大）。多数业务选至少一次加幂等。

**可靠性**：副本机制，ISR 集合，`acks=all` 加 `min.insync.replicas` 保证写成功时至少 N 个副本有数据；leader 挂掉从 ISR 里选新 leader，靠 HW（高水位）和 leader epoch 防止数据截断；消费者位点不能超过 HW，否则会读到可能被回滚的数据。

**失败处理**：消费失败进重试队列（按延迟分级），超过次数进死信队列并告警；业务侧必须有幂等，因为重试必然带来重复。消息保留按时间或大小，日志压缩（compaction）用于保留每个 key 的最新值。

**顺序性**：只保证单 partition 内有序，需要全局有序就只能单分区，吞吐会受限，所以一般按业务 key 分区。

**运维**：核心指标是消费延迟（lag）、ISR 收缩、磁盘使用、请求队列时间；再平衡（rebalance）要尽量少触发，避免消费者长时间不提交心跳被踢出组导致重复消费。

如果是让我选现成的：日志型、要吞吐和回溯选 Kafka；要事务消息、延迟消息、死信这些业务特性选 RocketMQ；只是做轻量异步和解耦，Redis Stream 就够（我短链统计就是这么做的），但它的可靠性和堆积能力远不如专门的消息队列。

#### Q19 地图：红绿灯倒计时 + 路况

两个问题分开看，红绿灯是「相位时间模型 + 下发」，路况是「数据采集 + 聚合 + 服务」。

**红绿灯倒计时**

核心是把信号机的配时方案建模，而不是去「预测」。一个路口有相位（Phase）、周期（Cycle）、绿信比，还有相邻路口的相位差（Offset）用于绿波带。数据来源优先级：交管部门对接（最准，能直接拿到配时方案和当前相位）> 车端/路侧设备上报（车辆排队起步、停车位置）> 用户众包。

服务端只下发「这个路口当前生效的配时方案 + 当前相位 + 相位开始时间戳 + 方案版本号」，客户端本地按时间戳自己算倒计时。这样做的原因是：每秒请求一次倒计时是不可行的，QPS 会按车辆数乘以秒数放大；本地推算只在「方案切换」「时间漂移」时才需要刷新。

工程上几个细节：

1. 客户端和服务端都要用统一时间源（NTP 校时或服务端下发时带 `serverTime` 做偏移校正），否则客户端时钟不准会导致倒计时偏差；
2. 下发用长连接或短轮询加缓存，key 是路口 ID，方案不变就命中缓存，TTL 到方案预计切换时间；
3. 方案变更、临时管制、感应控制（自适应配时）时主动失效缓存并推送变更；
4. 覆盖不到的路口宁可不下发，不要给错数据，用户按错误倒计时冲路口比没有数据更危险；置信度低的用「建议减速」这种模糊提示；
5. 兜底：用历史同期配时方案做先验，再用实时上报修正。

**路况判断**

1. 路网建模：把道路切成 link（路口之间的一段），link 是统计和下发的最小单位，再按方向、车道细分；
2. 数据采集：浮动车 GPS（自有车辆、合作方、用户授权定位）、地磁/雷达/卡口、交管事件（事故、施工、管制）、用户上报；
3. 地图匹配：GPS 点有误差，要把点吸附到具体 link 上，常用隐马尔可夫模型（候选路段 + 转移概率 + 发射概率），否则速度会算到隔壁路上去；
4. 聚合：按 link 和时间窗口（比如 1 分钟）算平均速度、流量、停车比例，剔除异常点（漂移、隧道、静止漂移）；
5. 判定：用速度和该 link 的限速/自由流速度比来分级（畅行、缓行、拥堵、严重拥堵），再结合停车比例和排队长度；时间上做平滑（指数平滑或卡尔曼），避免红绿灯造成的周期性抖动被误判成拥堵；
6. 存储与服务：时序数据按 link 存（比如时序库或 HBase 宽表），热数据进 Redis；对外按地图瓦片/栅格聚合下发，配合增量推送（只推变化的 link）和短 TTL 缓存；
7. ETA：实时速度 + 历史同期速度做加权，路口再叠加一个期望等待时间（由信号配时和排队长度估），这样比纯距离除以速度准得多；
8. 冷启动和稀疏：没有实时数据的 link 用历史同期模型兜，覆盖度要作为质量指标监控。

面试里如果只能讲一段，我会讲「link + 时间窗聚合 + 地图匹配 + 平滑」，因为路况不准的根源通常不在算法，而在点吸错了路、或者把红灯当拥堵。

#### Q20 手撕：全排列

原题是 **ACM 模式**：给一个 `n`（范围较小），求 `1~n` 的全排列并输出。元素是 `1..n` 且互不相同，所以最简单的是「按位填数 + `used` 标记」回溯，`v` 从 1 到 n 枚举，**结果天然是字典序**：

```cpp
#include <cstdio>

int n, path[15];
bool used[15];

// depth：已经填好了几个位置
void dfs(int depth) {
    if (depth == n) {
        for (int i = 0; i < n; ++i)
            printf("%d%c", path[i], i + 1 == n ? '\n' : ' ');
        return;
    }
    for (int v = 1; v <= n; ++v) {
        if (used[v]) continue;
        used[v] = true;
        path[depth] = v;
        dfs(depth + 1);
        used[v] = false;            // 回溯：撤销选择
    }
}

int main() {
    if (scanf("%d", &n) != 1) return 0;
    dfs(0);
    return 0;
}
```

写法二：直接调 `std::next_permutation`，短很多。但**数组必须先升序**，因为它只从当前排列往后枚举，乱序会漏：

```cpp
#include <cstdio>
#include <algorithm>

int main() {
    int n;
    if (scanf("%d", &n) != 1) return 0;
    int a[15];
    for (int i = 0; i < n; ++i) a[i] = i + 1;   // 必须升序
    do {
        for (int i = 0; i < n; ++i)
            printf("%d%c", a[i], i + 1 == n ? '\n' : ' ');
    } while (std::next_permutation(a, a + n));
    return 0;
}
```

ACM 模式下几个必须注意的点：

1. **输出顺序**：`v` 从小到大枚举，结果就是字典序（`1 2 3`、`1 3 2`、`2 1 3`……）。有些题（比如洛谷 P1706）还要求每个数字**固定 5 个场宽**，那输出那行就换成 `printf("%5d", path[i]);`（包括最后一个数后面也带空格，按题目要求来）。
2. **输出量很大**：`n!` 行、每行 `n` 个数，n=9 就是 362880 行。用 `printf` 足够；如果还卡常，就攒一个 `char buf[]` 一起 `fwrite`，或者用 `putchar_unlocked` 手写整数输出。**别用 `cout` 逐行打**（不关同步会很慢，至少要 `ios::sync_with_stdio(false)`）。
3. **输入**：`scanf` 够用；多组数据或超大输入再上 `getchar()` 快读。
4. **数组开够**：`path[15]`、`used[15]` 这种按题目 n 的上界开，别按 `n+1` 动态开——ACM 题 n 一般不超过 10，静态数组最省事，递归深度也只有 n，不会爆栈。
5. **这里不用交换法**：交换法也能枚举全，但输出**不是字典序**，题目一要求字典序就得额外排序，没必要。

复杂度上，答案本身的规模就是 `n · n!` 个数字，所以任何写法的时间下界都是 `O(n · n!)`，空间是递归栈加路径 `O(n)`（`next_permutation` 版是迭代、额外空间 `O(1)`）。

---

如果题目给的是**任意数组**（甚至含重复元素），就排序后用 `used` 去重，同一层里跳过相同的值：

```cpp
#include <cstdio>
#include <algorithm>

int n, nums[15], path[15];
bool used[15];

void dfs(int depth) {
    if (depth == n) {
        for (int i = 0; i < n; ++i)
            printf("%d%c", path[i], i + 1 == n ? '\n' : ' ');
        return;
    }
    for (int i = 0; i < n; ++i) {
        if (used[i]) continue;
        // 同一层里，值相同且前一个还没被用，说明这一支已经枚举过了
        if (i > 0 && nums[i] == nums[i - 1] && !used[i - 1]) continue;
        used[i] = true;
        path[depth] = nums[i];
        dfs(depth + 1);
        used[i] = false;
    }
}

int main() {
    if (scanf("%d", &n) != 1) return 0;
    for (int i = 0; i < n; ++i) scanf("%d", &nums[i]);
    std::sort(nums, nums + n);          // 去重的前提：有序
    dfs(0);
    return 0;
}
```

三种写法取舍一句话：**`1~n` 的 ACM 题用 `used` 标记法（字典序、直接输出，最稳），图省代码用 `next_permutation`（必须先升序），有重复元素才需要排序加 `used` 去重**。

同样的逻辑换 Java 写就是 `boolean[] used` + `StringBuilder` 攒输出，差别只在输出那一步；面试现场如果语言不限，回溯我用 C++ 写，省掉装箱和 IO 的干扰。

### 东软集团

#### 技术掌握情况与不足

诚实说就是：常用中间件「用过但不够深」。具体来说，Spring 的 IoC/AOP 和事务传播能讲清，并发和线程池能落到项目代码，MySQL 的索引和事务能讲到源码机制；不足在 JVM 调优（只做过基础参数和排查工具，没有真实调优案例）、分布式理论（只实践过最终一致，没做过分布式事务）、以及没有线上故障处理经验。

#### MySQL 的索引（相对熟）

InnoDB 用 B+ 树。选 B+ 树而不是 B 树：非叶子节点只存键不存数据，同样大小的页能放更多键，树更矮，磁盘 IO 更少；数据都在叶子节点且叶子之间用链表连起来，范围查询和排序可以顺序扫。

聚簇索引：主键索引的叶子节点直接存整行数据，一张表只有一个。二级索引的叶子存的是主键值，所以二级索引查到主键后还要回表再查一次聚簇索引。覆盖索引就是查询的列全在索引里，不用回表，`explain` 里 `Extra` 显示 `Using index`。

几个关键点：

1. 最左前缀，联合索引 `(a,b,c)` 能用于 `a`、`a,b`、`a,b,c`，跳列会断；范围查询后面的列用不上索引；
2. 失效场景：对索引列做函数或运算、隐式类型转换（字符串列传数字）、`like '%x'`、`or` 里有非索引列、区分度太低（性别）优化器直接不选；
3. 索引下推（ICP）：MySQL 5.6 之后把 where 里能用索引列判断的条件下推到存储引擎层，减少回表；
4. 索引不是越多越好，每个索引都增加写放大和存储，还会影响优化器选择；
5. 自增主键的好处是顺序插入，避免页分裂。

#### MySQL 的缓存机制（Buffer Pool）

不是缓存 SQL 结果（8.0 已经把 query cache 删了），而是缓存数据页。Buffer Pool 是内存里的一块区域，按 16KB 的页管理，读写都先经过它，脏页由后台线程刷回磁盘。默认 `innodb_buffer_pool_size` 在 8.0 是 128MB，生产上一般给到物理内存的 50%-70%；buffer pool 大于 1GB 时会分成多个 instance（默认 8 个），每个有自己的锁，减少竞争。

内部几个链表：free list 放还没用过的空闲页；LRU list 管已缓存的页；flush list 按最早修改的 LSN 排序，标记哪些是脏页；还有 unzip LRU 用于压缩表。

LRU 做过改进，因为全表扫描或预读会把热数据挤出去。它把链表分成 young（约 5/8）和 old（约 3/8），新页从中间 midpoint 插入到 old 区头部；只有当页在 old 区停留超过 `innodb_old_blocks_time`（默认 1000ms）之后再次被访问，才晋升到 young 区。这样一次性扫描的大量页只在 old 区快速淘汰，不会污染热数据。

另外还有 change buffer：对非唯一二级索引的写操作，如果页不在内存里，先记在 change buffer，等页被读进来再合并，减少随机读；自适应哈希索引是 InnoDB 自己观察到某些页被频繁等值查询后建的哈希索引；预读分线性预读和随机预读。

判断缓存够不够看命中率：`Innodb_buffer_pool_read_requests` 和 `Innodb_buffer_pool_reads` 的比值，低于 95% 一般说明内存给少了。

#### 日志

三个日志要分清层级和作用：

| 日志 | 层级 | 内容 | 作用 |
| --- | --- | --- | --- |
| redo log | InnoDB | 物理日志，某页做了什么修改 | 崩溃恢复，保证持久性。环形文件，checkpoint 推进 |
| undo log | InnoDB | 逻辑日志，记录反向操作 | 事务回滚（原子性）加 MVCC 版本链 |
| binlog | Server | 逻辑日志，记录变更 | 主从复制、时间点恢复、订阅变更 |

还有 relay log 在从库，是中转站。redo 和 binlog 需要两阶段提交，因为一个在引擎层一个在 Server 层，不一致会导致主从永久不一致。

#### 深入数据库的意愿

愿意。理由是数据库是后端最容易「一知半解就出事」的地方：一条没走索引的 SQL、一个长事务、一次大 key 删除，都能直接把线上打挂，而这类问题的判断只能来自对机制的了解。具体想补的方向是执行计划和优化器（为什么不选索引）、锁与并发（间隙锁、死锁检测）、以及 InnoDB 的存储与刷盘（页结构、redo 刷盘策略、崩溃恢复）。
