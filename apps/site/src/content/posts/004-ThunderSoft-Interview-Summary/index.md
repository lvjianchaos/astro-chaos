### Q7 HashMap 线程不安全 / ConcurrentHashMap / CAS

> HashMap 线程不安全，主要有四个原因。
>
> **第一个是 put 的"判断-写入"不是原子的。** HashMap 先算 hash 定位到桶，然后判断桶是不是空的，如果是空的就直接放一个新建的 Node；如果不是空的，就走链表或者红黑树往下插入。这两步之间有时间差，两个线程可能同时判断到"桶是空的"，然后各建一个 Node，后写的把先写的覆盖掉，**数据就丢了**。
>
> **第二个是扩容 resize 不是原子的。** JDK7 用头插法迁移节点，并发扩容会导致链表成环、死循环把 CPU 打满；JDK8 改成尾插法，解决了成环，但**丢数据的问题依然存在**——扩容期间 put 的元素可能写进旧数组，扩容完旧数组就被丢掉了。
>
> **第三个是 size++ 不是原子的**，它是普通 int 的读-改-写，并发下计数会不准。所以 JDK8 把计数改成了 baseCount 加 CounterCell 的方式，接近 LongAdder 的思路，而且 size() 返回的是**近似值**。
>
> **第四个是 get 也可能读到半成品**，Node 的 value 不是 volatile，并发扩容时可能读到 value 是 null 但 next 已经设置好的节点。
>
> ---
>
> ConcurrentHashMap 在 **JDK8 抛弃了 JDK7 的分段锁**，改成了 **CAS 加 synchronized**。
>
> **读操作完全不加锁**：table 数组、Node 的 val 和 next 都是 volatile 修饰的，保证可见性；数组元素可能是 null，那说明正在扩容，get 的时候会继续重试查找。
>
> **写操作分三种情况**：桶是空的，就用 **CAS** 把新节点放进去；桶非空且是链表，就 **synchronized 锁住桶头节点**，再插入，超过 8 个节点且数组长度到 64 就转成红黑树；桶已经是红黑树，就锁 TreeBin 节点。
>
> **扩容是多线程协助的**：用 sizeCtl 记录扩容进度和目标大小，用 transferIndex 记录迁移到哪个位置了，每个线程一次迁移一批。已经迁移完的桶会放一个 **ForwardingNode** 占位，别的线程读到这个节点就知道该表正在扩容，可以去帮忙一起搬，**所以扩容期间读不会阻塞，也不会丢数据**。
>
> ---
>
> **CAS 就是 Compare-And-Swap**，一条 CPU 原子指令，语义是"如果内存里这个值等于我期望的值，就改成新值，返回成功；否则什么都不做，返回失败"。它的关键是**比较和交换这两步不可分割**，这是所有无锁算法的基石。
>
> 典型用法是 AQS 里的 compareAndSetState、ConcurrentHashMap 里的 CAS 插入、还有各种 Atomic 原子类。
>
> CAS 的局限也很明确：**它只能保证单个变量的原子性**，多个变量的复合操作还是得用锁；另外就是 **ABA 问题**——CAS 只比较值不看历史，A 改成 B 又改回 A，CAS 以为没变过其实变了，解法是加版本号，比如 AtomicStampedReference。还有 CAS 是自旋，**高竞争下会白烧 CPU**，临界区很短的时候才划算。

| **"CAS 一定比锁快吗？"**                                    | 不一定。CAS 适合**临界区极短**的场景；临界区长的话自旋会白烧 CPU，反而不如阻塞锁。JDK8 的 CHM 用 synchronized 而不是 ReentrantLock，正是因为临界区（链表插入）非常短。 |
| **"ABA 怎么解决？实际项目遇到过吗？"**                      | 解决：加版本号/时间戳（`AtomicStampedReference`），或者 AQS 那种把状态设计成单调递增的语义。我的项目里 `ModelHealthStore` 用 `ConcurrentHashMap.compute`，状态迁移是**原子的**，就不会出现"两个线程都以为是 OPEN"的问题。 |

#### ⚠️ 三个别踩的坑

1. **别说"ConcurrentHashMap 就是加了锁的 HashMap"** —— 它的读是**完全无锁**的，这是最大的卖点。
2. **别说"用 volatile 就能保证 HashMap 线程安全"** —— volatile 只保证可见性，不保证原子性，`i++` 照样错。
3. **别把 JDK8 的扩容说成"原子操作"** —— 是**多线程协作**完成的，靠 ForwardingNode 引导。

#### 🔗 项目关联

> 我项目里其实用到了 CHM 的一个高级特性：`ConcurrentHashMap.compute(id, ...)`。我的模型健康状态存储就是 `ConcurrentHashMap<String, ModelHealth>`，熔断状态迁移是"检查状态 → 改成半开 → 置探测在途标志"这么一串复合操作。如果我写成 `get` 判断再 `put` 回写，这三步之间就有竞态，可能两个线程同时把 OPEN 迁移成 HALF_OPEN、同时放两个探测请求进来。**`compute` 会在桶级锁保护下执行整个 lambda，保证这串操作原子**，这跟我刚才说的 AQS 的 `compareAndSetState` 是同一个思路——**用原子操作保护状态机迁移，而不是用 if-else 拼出来的"看起来对"的代码**。

### Q8 wait() 和 sleep() 的区别

> 主要有四个区别。
>
> **第一，wait 是 Object 的实例方法，sleep 是 Thread 的静态方法。** sleep 是给整个当前线程延时，谁调用都一样；wait 是针对某个对象的监视器。
>
> **第二，调用前提不同。** wait 必须在 **synchronized 块里**、必须持有那个对象的锁才能调用，否则直接抛 `IllegalMonitorStateException`；sleep 没有任何前置条件，任意线程都能调。
>
> **第三，也是最关键的：wait 会释放锁，sleep 不会。** wait 的语义是"我等这个对象的状态变化"，而状态的改变通常需要别的线程去操作这个对象——最典型的就是生产者消费者。消费者 wait 在共享缓冲区上，生产者必须能拿到同一把锁才能往里放数据。**如果 wait 不释放锁，生产者永远进不来，就直接死锁了。**
>
> sleep 只是单纯让线程停一会儿，**如果当前线程正好持有锁，sleep 期间这把锁还一直在别人手里**，别人全在排队。
>
> **第四，唤醒方式不同。** wait 靠 notify、notifyAll 或者被 interrupt 唤醒，醒来之后还要**重新去竞争锁**才能往下走；sleep 靠时间到自然醒，或者被 interrupt。
>
> ---
>
> 使用场景上：**wait 用在条件等待**，比如生产者消费者、线程池里阻塞队列的 take；**sleep 用在定时和调度**，比如轮询间隔、重试退避、限流等待。
>
> 另外有个实践上的坑要提醒一下：**wait 必须写在 while 循环里，不能用 if**。因为一是 JVM 允许虚假唤醒，二是被唤醒后到重新拿到锁之间，条件可能已经被别的线程抢走了。规范写法是 `synchronized(lock) { while(!条件成立) lock.wait(); doSomething(); }`。

#### 🔍 追问表

| 他会追问                                                   | 你怎么答                                                     |
| ---------------------------------------------------------- | ------------------------------------------------------------ |
| **"notify 和 notifyAll 有什么区别？"**                     | notify 随机唤醒一个等待线程，notifyAll 唤醒全部。**规范做法是用 notifyAll**——用 notify 可能唤醒一个"条件其实不满足"的线程（比如队列里还有元素，消费者被唤醒却没数据），造成信号丢失。 |
| **"wait 唤醒后为什么还要重新竞争锁？"**                    | 因为 wait 释放了锁，醒来时锁可能已经被别的线程拿走了。wait 的语义是"回到竞争这个对象的入口排队"，不是"直接恢复执行"。 |
| **"sleep 会释放锁吗？会释放什么？"**                       | 什么都不释放。但注意 **sleep 期间会持有它已经持有的所有锁**。另外 sleep 也不释放"CPU"，它只是让出 CPU 时间片，状态是 TIMED_WAITING。 |
| **"notifyAll 之后被唤醒的线程怎么保证只有一个拿到数据？"** | 靠 wait 里的 while 循环 + 重新检查条件 + 拿到锁后重新判断。被唤醒的线程如果发现条件不成立，会**再次 wait 回去**。 |

- **别说"wait 和 sleep 都会释放锁"或"都不会"** —— wait 释放、sleep 不释放，这是唯一的正确记法。
- **别忘了提"必须在 synchronized 里调用"** —— 这是 IllegalMonitorStateException 的来源，也是"wait 为什么能释放锁"的前提。

### Q9 泛型与泛型擦除

> Java 的泛型是**编译期特性**，也叫类型擦除。编译的时候做三件事。
>
> **第一，做类型检查。** `List<String>` 里放一个 Integer，编译期就报错。
>
> **第二，插入类型转换。** 这就是最关键的一点：写 `String s = list.get(0)` 的时候，编译器会自动在字节码里插入一个 **checkcast**，也就是 `(String) list.get(0)`。**所以泛型本质上就是"编译器帮你写 cast"，运行时这个 cast 是真实存在的**，后面会讲它带来的问题。
>
> **第三，做类型擦除。** 编译成字节码的时候，类型变量被替换成它的**上界**——没有指定上界就替换成 Object，有上界就替换成上界；通配符 `? extends T` 替换成上界，`? super T` 替换成 Object。**所以 `List<String>` 和 `List<Integer>` 编译出来的字节码是完全一样的**，运行时都是同一个 ArrayList 类。
>
> 擦除发生在**编译期**，不是运行期，这一点很重要。
>
> ---
>
> 擦除带来的影响有这么几个。
>
> **最典型的是堆污染。** 如果我用了原始类型，`List list = new ArrayList(); list.add("hello");` 编译器就管不了了，它没法检查。然后我 `String s = (String) list.get(0)`，运行时就可能抛 **ClassCastException**。这就是 unchecked warning 的来源。
>
> 另外，**没法 new 一个 T 数组**，也没法写 `instanceof List<String>`，因为类型信息已经被擦掉了，`instanceof List<?>` 是合法的，但 `instanceof List<String>` 编译期就报错。
>
> 还有，**没法按具体类型重载**——`f(List<String>)` 和 `f(List<Integer>)` 擦除之后签名一样，编译不过。也不能继承具体参数化的父类，`class MyList extends ArrayList<String>` 是错的。
>
> ---
>
> 还有一个细节叫**桥方法**。比如 `class A implements Comparable<A>`，擦除之后 `Comparable` 的签名是 `compareTo(Object)`，编译器会生成一个**桥方法** `compareTo(Object)`，内部做一次强转再转调真正的 `compareTo(A)`。**桥方法保证了擦除之后多态还是正确的**，这也是为什么 `Collections.sort` 能正常工作。
>
> 最后，泛型还有个约束：Java 的泛型**不支持协变**，`List<String>` 不是 `List<Object>` 的子类型。要表达"接收任意 Number 列表"这种需求，就用通配符，按 **PECS 原则**：Producer 用 extends，Consumer 用 super。

#### 🔍 追问表

| 他会追问                             | 你怎么答                                                     |
| ------------------------------------ | ------------------------------------------------------------ |
| **"泛型信息完全消失了吗？"**         | 不是。**类、字段、方法声明上的部分泛型信息会保存在 class 文件的 Signature 属性里**，可以通过反射读到 `getGenericType()`。但你**不能**从一个普通的 `new ArrayList<String>()` 对象直接反推出它的类型参数是 String。 |
| **"泛型为什么不能协变？"**           | 因为泛型是编译期擦除的，运行时 `List<String>` 和 `List<Integer>` 是同一个类，JVM 无法在运行时区分，强行协变会导致 `List<Object>` 里能塞进 Integer，类型安全彻底崩掉。所以用通配符来表达受限的协变/逆变。 |
| **"PECS 是什么？"**                  | Producer Extends, Consumer Super。`List<? extends Number>` 只能读出 Number，`List<? super Integer>` 只能写 Integer。标准库 `Collections.copy(List<? super T> dest, List<? extends T> src)` 就是这么写的。 |
| **"桥方法是干什么的？为什么会有？"** | 保证擦除后的多态正确性。父类 `compareTo(Object)`，子类重写 `compareTo(A)`，编译器生成桥方法做适配。 |
| **"泛型方法和泛型类有什么区别？"**   | **泛型方法**：`<T> T func(T a)`，类型变量由方法自己声明，调用时推断，可以是**静态方法**；**泛型类**：`class Box<T>`，类型变量属于整个类，成员方法都能用，且**成员变量不能用类的类型参数**（`T field` 不合法，因为每个实例的 T 可能不同，会破坏类型安全）。 |
| **"项目里怎么用泛型？"**             | 我 RAGent 里的 `RetrievedChunk`、`SearchChannelResult` 这些 DTO 都用了泛型；`ModelRoutingExecutor.executeWithFallback` 用了两个类型参数 `<C, T>`，把"客户端类型"和"返回类型"解耦，让 chat / embedding / rerank 三种能力能复用同一套降级逻辑。 |

#### ⚠️ 别踩的坑

1. **别说"泛型在运行时被擦除"** —— 擦除是**编译期**做的，运行时的字节码里本来就没有泛型信息。
2. **别漏掉"编译器插入 checkcast"** —— 这是理解堆污染和 CCE 的钥匙，也是这道题区分"背过"和"懂了"的分水岭。

### Q10 反射的底层实现与使用场景

> 反射就是**在运行时获取类的结构信息，并动态创建对象、调用方法、访问字段**的机制。
>
> 它的核心是 `Class` 对象。编译后的类在 JVM 里以 `Class` 对象的形式存在，类的元数据——字段、方法、构造器、注解——在元空间里。反射就是通过 `Class` 拿到 `Method`、`Field`、`Constructor` 这些对象，再去操作。
>
> ---
>
> **底层调用链**是这样的：`Method.invoke(obj, args)` 会先做**访问检查**，JDK 9 之后访问检查做了缓存优化；然后通过 `MethodAccessor` 调到 native 的 `invoke0`，**走 JNI 进入 C++**，最终由 **JVM_InvokeMethod 通过虚方法表分派**找到真正的目标方法并执行。
>
> 这里有个关键点：**反射最终还是要走虚方法表分派**，所以**被重写的方法能被正确调用，多态是安全的**。反射慢是因为多了参数装箱、访问检查，还有 MethodAccessor 的间接跳转，而且**没法被 JIT 内联**。JDK 8 之后 `MethodHandle` 的性能就接近直接调用了，因为它签名多态，编译器能内联。
>
> ---
>
> **使用场景**我按层次说。
>
> **第一层是框架基础设施**，这是最主要的。Spring 的 IoC 容器扫描 `@Component` 注解后用反射创建实例、注入依赖；MyBatis 的 Mapper 是用 **JDK 动态代理**加反射执行 SQL 的；Jackson 序列化是反射读 getter；Spring MVC 的 `@RequestMapping` 是反射找处理方法；JUnit 4 是反射调 `@Test` 方法。
>
> **第二层是动态代理和字节码增强**。`Proxy.newProxyInstance` 加 `InvocationHandler` 是 JDK 动态代理，只能代理接口；CGLIB 和 ByteBuddy 是生成子类，可以代理类，**Spring AOP 的 `@Transactional` 默认走的就是 CGLIB**。
>
> **第三层是插件化和 SPI**。`Class.forName` 动态加载驱动，JDBC 的 `DriverManager` 就是这么干的，Spring Boot 的自动装配也是。
>
> 第四层是通用工具类，比如 `BeanUtils.copyProperties` 底层是反射拷贝属性。
>
> ---
>
> **反射的代价**也很明确：它把编译期的检查推迟到了运行时，方法名写错要到运行才发现；`setAccessible(true)` 能绕过访问控制，破坏封装，JDK 9 的模块系统会限制这个，JDK 16 之后强封装了 JDK 内部；还有性能开销。
>
> 所以我的原则是：**反射是框架边界上的手段，不是业务代码的日常写法**。需要动态行为的时候优先用接口加策略实现类，编译期可控、可多态、也能 mock；反射只留给框架层。

| ----------------------------------------------- | ------------------------------------------------------------ |

#### 🔗 项目关联

> 说实话，我项目里**业务代码基本不用反射**，但我对它的理解是通过框架学到的。Spring 本身就是反射的集大成者——我的项目里 `@Transactional` 的事务边界、`@RequestMapping` 的路由匹配、MyBatis 的 Mapper 代理，全都是反射在底层工作。而且反射在注解处理这块也是核心：Spring 的 `@Autowired`、`@Value` 是先通过反射拿到注解，再反射读写字段完成注入的。这让我形成一个判断：**反射是框架的底层能力，业务层应该优先用接口和多态来表达可变性**，这也让代码更容易测试和 mock。

### Q11 死锁：成因、排查、解决

> 死锁要**同时满足四个必要条件**：**互斥**、**持有并等待**、**不可剥夺**、**循环等待**。打破任意一个就能预防。
>
> ---
>
> 解决上我分三层。
>
> **预防层面，最常用的是资源有序分配法**：给资源定义一个顺序，所有线程都按同一个顺序申请资源，就不可能形成环。其次是用**带超时的 `tryLock`**——拿不到就释放已有锁、结束或有限重试，这破坏了"不可剥夺"条件。还有一条很实用的：**不要在持锁期间做长时间的远程调用**。
>
> **避免层面**，用更高层的并发工具替代裸锁嵌套：用 `ConcurrentHashMap.computeIfAbsent` 这种同 key 串行的原子方法、用线程池做业务隔离、用 `CountDownLatch`、`Semaphore`、`CompletableFuture` 这些 JUC 工具。
>
> **检测层面**，线上用 `jcmd <pid> Thread.print -l` 或者 `jstack -l <pid>` 抓线程栈，看哪些线程 BLOCKED 在哪把锁上，栈里会直接打印 "Found one Java-level deadlock"。代码层面可以用 `ThreadMXBean.findDeadlockedThreads()`。
>
> 顺便提醒一个坑：**给线程发 interrupt 并不能解除 synchronized 的锁等待**，它只能中断 `wait`、`sleep` 和可中断的锁获取。
>
> ---
>
> 我自己的项目里**没有真正触发过死锁**，但我在设计时刻意规避了。我的做法是：**永远不在临界区里嵌套获取第二把锁**，这样根本形不成环；**锁的粒度按业务 key 细分成不同的锁**，避免热点；以及**跳转这种高并发路径用 `tryLock` 带超时而不是 `lock()`**，拿不到锁就降级返回，绝不让线程无限堆积在锁上——因为**锁竞争演变成雪崩比死锁更常见也更致命**。

#### 🔍 追问表

| 他会追问                              | 你怎么答                                                     |
| ------------------------------------- | ------------------------------------------------------------ |
| **"你怎么在代码里发现死锁的？"**      | `jstack` / `jcmd Thread.print -l`，或者 IDEA 的 "Debug → Threads"，或者 Arthas 的 `thread -b`（专门打印阻塞线程）。工具能识别**监视器锁**和**可拥有同步器（AQS）**的死锁，但**识别不了所有业务层面的互相等待**（比如两个线程在等对方发 HTTP 响应）。 |
| **"能不能举个真实死锁的例子？"**      | 经典的两把锁：线程1 持有 A 请求 B，线程2 持有 B 请求 A。另一个高频场景是**嵌套调用带 @Transactional 的方法**，或者**线程池任务里再提交任务到同一个池**（任务互相等待对方执行完 → 死锁）。 |
| **"分布式环境怎么防死锁？"**          | 分布式锁本身就是"死锁高发区"。要点：**① 一定用 tryLock 带超时，不要用 lock()**；**② 业务执行时间必须小于锁的租约时间**，否则锁过期被别的线程拿到，两个线程同时进临界区 → 数据错乱（Redisson 的看门狗自动续期就是解决这个的）；**③ `finally` 里必须 unlock**，防止异常导致锁泄漏；**④ 减少锁嵌套**。 |
| **"怎么避免 Redis 分布式锁被误删？"** | 三种：① **看门狗续期**（Redisson 默认，持有者存活时自动续租）；② **value 带唯一标识 + Lua 脚本原子校验后再删**（只删自己的锁）；③ **用 zookeeper 的临时顺序节点**（session 断开自动删除）。 |
| **"死锁和饥饿有什么区别？"**          | 死锁是**所有相关线程都被永久阻塞**；饥饿是**某个线程因为优先级低/调度不公，一直拿不到资源，但系统整体还在推进**（比如非公平锁下某个线程一直抢不到）。 |

#### ⚠️ 别踩的坑

1. **别说"死锁可以靠 interrupt 解决"** —— interrupt 解不了 synchronized 的锁等待。
2. **别只背四个条件不说怎么破** —— 他问的是"怎么解决"，要给出**统一加锁顺序 + tryLock 超时**这两个最实战的。

#### 🔗 项目关联

> 我短链项目里最容易出死锁的地方是**跨分组迁移短链**那段：一个线程要同时改旧 gid 的记录和新 gid 的记录，还要同步更新路由表。我用 Redisson 的读写锁，key 是 `LOCK_GID_UPDATE_KEY + fullShortUrl`，也就是**同一把锁保护同一件事、不同短链互不阻塞**。而且锁内我**没有再获取第二把锁**，所以不存在等待环。跨组迁移的顺序也是固定的：先在旧 gid 上软删，再在新 gid 插入，最后更新路由表——**固定顺序 + 单锁 + 细粒度**，这三个就够防死锁了。

### Q13 JVM 类加载机制

> 类的完整生命周期是：**加载、验证、准备、解析、初始化、使用、卸载**。中间三个"验证准备解析"叫**链接**。
>
> **加载**：通过类的全限定名获取二进制字节流，来源可以是 jar、class 文件甚至网络；然后在内存中生成一个代表这个类的 `Class` 对象，作为访问入口。
>
> **验证**：文件格式、元数据、字节码、符号引用四类校验，保证不危害虚拟机自身安全。
>
> **准备**：给类变量也就是 static 字段**分配内存并赋零值**。这里有个细节要强调：**赋的是零值，不是源码里写的值**。`static int x = 5` 在准备阶段是 0；但 `static final int LIMIT = 100` 这种带 ConstantValue 属性的编译期常量，会直接赋成 100。
>
> **解析**：把常量池里的**符号引用**替换成**直接引用**，也就是内存地址。这个阶段可以延迟到真正使用的时候才做。
>
> **初始化**：执行 `<clinit>()` 方法。注意它**不是**我们写的构造器 `<init>()`，而是**编译器自动收集所有静态变量赋值语句和静态代码块合并生成的**。
>
> ---
>
> **触发初始化的场景**可以记一个关键词：**主动使用**。new 一个对象、读写静态字段（读编译期常量除外）、调用静态方法、反射主动使用、初始化子类时先初始化父类、JVM 启动时初始化主类。
>
> 反过来，**引用编译期常量**、**定义数组**、**引用类字面量 `X.class`** 都不会触发初始化——注意 `Class.forName("X")` 会触发，但 `X.class` 不会。
>
> ---
>
> **双亲委派**是类加载的核心。
>
> 层次上，JDK 8 是：**启动类加载器 Bootstrap**（C++ 实现，加载 `java.*` 等核心类）、**扩展类加载器 Extension**、**应用类加载器 Application**（加载 classpath），下面可以自定义。**JDK 9 起扩展类加载器被 Platform ClassLoader 取代。**
>
> 规则是：**收到加载请求先委派给父加载器，父加载器搞不定自己才加载**，一直递归到最顶层的 Bootstrap。
>
> 它的作用有三个：**① 保证类的唯一性**——同一个类只由一个加载器加载一次，不会出现两个不同的 Class 对象；**② 保护核心类库**——应用自己写个 `java.lang.String` 是没用的，因为 Bootstrap 会优先加载；**③ 复用核心类**，减少内存消耗。
>
> 这里有个细节要说清楚：**"双亲"不是继承关系，是加载器之间的委派关系**；而且**双亲委派不保证整个 JVM 里同名类只有一份**——不同的自定义加载器各自定义的同名类，在 JVM 看来是不同类型。
>
> ---
>
> **破坏双亲委派的场景**：
>
> **① SPI**：JDBC 驱动接口在 JDK 里，由 Bootstrap 加载，但实现类在第三方 jar 里。`ServiceLoader` 通过**线程上下文类加载器**反向找到应用加载器去加载实现。
> **② Tomcat**：每个 Web 应用一个 `WebappClassLoader`，实现应用隔离，而且对 Java 核心类**优先加载**，不委派给父。
> **③ OSGi**：每个 Bundle 一个加载器，网状依赖。
> **④ 热部署和字节码增强**（CGLIB、Mockito、MyBatis 的 Mapper），需要在目标 ClassLoader 里生成类。
>
> 最后，**类的卸载**条件很苛刻，要**同时**满足三条：所有实例都被回收、定义它的 ClassLoader 被回收、Class 对象没有任何地方引用（包括反射）。

#### 🔍 追问表

| 他会追问                                              | 你怎么答                                                     |
| ----------------------------------------------------- | ------------------------------------------------------------ |
| **"自定义类加载器要重写 loadClass 还是 findClass？"** | **如果只是想改变"从哪里读 class 文件"，重写 `findClass()` 就行，而且这样还保留了双亲委派**；只有当你需要"优先加载自己范围内的某些类"时，才重写 `loadClass()` 改成子优先。 |

| **"静态初始化块抛异常会怎样？"**                      | 类进入**初始化失败**状态。第一次通常是 `ExceptionInInitializerError`，后续再次主动使用会抛 `NoClassDefFoundError: Could not initialize class`。所以看到 NoClassDefFoundError 也要检查是不是之前初始化失败过。 |
| **"接口的初始化规则和类一样吗？"**                    | 不一样：**初始化一个接口不会自动初始化它所有的父接口**；但如果接口里**声明了 default 方法**，且这个接口被实际使用，那么**声明了 default 方法的相关父接口**要先初始化。 |

#### ⚠️ 别踩的坑

1. **别说"准备阶段给 static 赋值成源码里的值"** —— 那是初始化阶段的事，准备阶段给的是**零值**。
2. **别把 `Class.forName` 和 `X.class` 搞混** —— 前者触发初始化，后者不触发。
3. **别说"双亲委派保证 JVM 里同名类只有一份"** —— 只在**同一个加载器**内才唯一。

#### 🔗 项目关联

> 我项目里最直接的例子是 **SPI**：`ServiceLoader` 加载 JDBC 驱动就是典型的"接口由 Bootstrap 加载、实现由应用加载器加载"这种反向委派。另外我用的 Redis 客户端 Redisson 里也大量用了反射和动态代理——`RLock` 的实现是通过动态代理把接口方法路由到真实的 Lua 脚本执行上；而 Spring 里 `@Transactional` 的 CGLIB 代理生成、MyBatis 的 Mapper 代理，都是在**运行期动态生成字节码**，这也解释了为什么这些框架的启动会有明显的类加载开销。

### Q14 == vs equals；只重写 equals 会怎样；只重写 hashCode 会怎样

> `==` 对**基本数据类型**比的是值，对**引用类型**比的是**引用地址**，也就是是不是同一个对象。`equals` 是 Object 提供的方法，默认实现就是 `==`，但可以重写成逻辑相等。
>
> ---
>
> 为什么重写 equals 就必须重写 hashCode？因为 **HashMap 的查找是两步**：第一步用 `hashCode` 定位桶，第二步在桶里用 `equals` 判断是不是目标。**hashCode 决定你能不能找到那个桶，equals 决定你能不能认出它。** 两个契约必须同时满足。
>
> hashCode 的契约是：**如果两个对象 equals 返回 true，它们的 hashCode 必须相等**；反过来，**hashCode 相等，equals 不一定相等**，因为允许哈希冲突。口诀是"**相等必有相同哈希码，但相同哈希码未必相等**"。
>
> ---
>
> **只重写 equals 不重写 hashCode 会怎样？**
>
> 两个业务上相等的对象，hashCode 还是 Object 的身份哈希码，**必然不同** —— 这就违反了契约。它们会被 HashMap 放进**不同的桶**，导致：**HashSet 里能同时放进两个"逻辑相等"的对象**，去重完全失效；`map.put(key, v)` 之后 `map.get(key)` **取不到**。
>
> 最迷惑人的现象是：**`list.contains(obj)` 返回 true，但 `set.contains(obj)` 返回 false** —— 因为 List 是逐个用 equals 比的，Set 是先比 hashCode 定位桶。这就是"我明明重写了 equals，为什么集合里还有重复"的经典 bug。
>
> **只重写 hashCode 不重写 equals 会怎样？**
>
> hashCode 相同 → 进同一个桶 → 但桶内还是用 equals 判断，而 equals 仍是引用比较 → **逻辑相等的对象依然被认为不相等**，去重照样失效。只是性能上变好了（所有对象挤在少数桶里）。
>
> 特殊地：如果两个对象 hashCode 相同但 equals 不同，它们会**冲突到同一个桶**，形成长链表，这就是 HashMap 要做 `hash ^ (hash >>> 16)` 扰动打散的原因。
>
> ---
>
> 所以结论是：**改 equals 必须同步改 hashCode；改 hashCode 不强制改 equals，但通常也一起改。**
>
> 实例上，String 两者都重写了：`hashCode = s[0]*31^(n-1) + s[1]*31^(n-2) + ...`，`equals` 逐字符比较。BigDecimal、BigInteger 也都正确重写了。而很多自定义 DTO 只重写了 equals，那就会踩坑——**Lombok 的 `@EqualsAndHashCode` 就是为了避免这个坑**。
>
> 最后还有一个实践建议：**对象作为 HashMap 的 key 之后，不要修改参与 equals 和 hashCode 计算的字段**，否则存的时候算的哈希值和查的时候算的不一样，就再也找不到了。

#### 🔍 追问表

| 他会追问                                              | 你怎么答                                                     |
| ----------------------------------------------------- | ------------------------------------------------------------ |
| **"重写 equals 用 `instanceof` 还是 `getClass()`？"** | 两种都有取舍。**`getClass()` 更严格**，但子类加了字段后 equals 会失效；**`instanceof` + `canEqual()` 钩子方法**更灵活，java.time 系列大量使用。**用 instanceof 时不用担心 null**，因为 instanceof 对 null 天然返回 false。 |
| **"hashCode 用 31 乘有什么讲究？"**                   | 31 是质数，且 `31 = 1<<5 - 1`，**左移减一等价于左移加一**，可以用位运算代替乘法。选质数是为了让哈希值分布更均匀，减少冲突。 |
| **"HashSet 底层是 HashMap 吗？"**                     | 是。`HashSet` 内部持有一个 `HashMap`，元素作为 key 存在，value 统一是一个 `PRESENT` 对象。所以 **HashSet 的去重完全依赖 equals + hashCode**。 |
| **"TreeSet 用什么比较？"**                            | 用 **TreeMap**，走的是**红黑树**，比较用的是 `compareTo`，不是 equals 和 hashCode。所以 **TreeSet 的元素必须实现 `Comparable`**，而且 compareTo 和 equals 的语义最好一致，否则会出现"contains 返回 false 但集合里有这个元素"的诡异现象。 |

#### ⚠️ 别踩的坑

1. **别说"hashCode 相同就说明对象相等"** —— 只能说 hashCode 相同**有可能**相等。
2. **别只说结论不说后果** —— "会导致 HashSet 去重失效"是结论，"**list.contains 是 true 但 set.contains 是 false**"才是让面试官眼前一亮的证据。

### Q15 MySQL MVCC + 日志体系

> MVCC 是多版本并发控制，它解决的是**读-写不阻塞**：写操作不会阻塞读，读操作也不会阻塞写，写和写之间靠行锁排队。实现的效果是数据库级别的**快照隔离**。
>
> 要补充一个点：**快照隔离本身不解决幻读**。MVCC 解决的是不可重复读，幻读在 InnoDB 里是靠 **Next-Key Lock** 在当前读时防住的。
>
> ---
>
> MVCC 的核心是**三样东西：隐藏字段、undo 版本链、Read View**。注意它**不是在开启事务的时候把整张表复制一份**。
>
> **隐藏字段**：InnoDB 聚簇索引的每行有三个隐藏列。`DB_TRX_ID` 是最后修改这一行的事务 ID；`DB_ROLL_PTR` 是回滚指针，指向 undo log 里的上一个版本；`DB_ROW_ID` 是隐藏自增主键，只有在表既没有主键也没有唯一索引时才生效。
>
> **版本链**：最新版本在聚簇索引里，它的 `DB_ROLL_PTR` 指向 undo log 中的上一版本，上一版本又有自己的回滚指针，就串成了一条从新到旧的链。
>
> **Read View** 有四个字段：
>
> - `m_ids`：创建 Read View 时，数据库里**活跃（已分配事务 ID 但未提交）**的事务 ID **列表**；
> - `min_trx_id`：这些活跃事务里最小的 ID；
> - `max_trx_id`：**不是 m_ids 的最大值**，而是创建 Read View 时**下一个要分配的事务 ID**，也就是全局最大事务 ID + 1；
> - `creator_trx_id`：创建这个 Read View 的事务 ID。
>
> ---
>
> **可见性判断算法**，对版本链上每个版本的 `trx_id` 依次判断：
>
> 1. `trx_id == creator_trx_id` —— **可见**，自己改的自己当然看得见；
> 2. `trx_id < min_trx_id` —— **可见**，创建 Read View 之前就已经提交了；
> 3. `trx_id >= max_trx_id` —— **不可见**，创建 Read View 之后才开启的事务；
> 4. 在 `min_trx_id` 和 `max_trx_id` 之间 —— **看它在不在 m_ids 里**：在，说明创建 Read View 时还没提交，**不可见**；不在，说明当时已经提交，**可见**。
>
> 不可见就顺着 `DB_ROLL_PTR` 沿版本链找下一个版本，按同样的规则判断，直到找到可见版本或者确认这条记录在当前快照里不存在。
>
> ---
>
> **快照读和当前读**要分清：
>
> **快照读**是普通的 SELECT，不加锁，靠 Read View 找可见版本。**读提交**下**每条 SELECT 都新建一个 Read View**；**可重复读**下**通常在第一次一致性读时创建 Read View，后续快照读复用**。这就是 RC 不可重复读、RR 可重复读的根源。
>
> **当前读**是 `SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE`、UPDATE、DELETE，读的是**最新版本**，而且**加行锁**。
>
> 一个容易混的点：**RR 下如果事务 A 先普通 SELECT 了，然后事务 B 插入并提交，A 再 UPDATE 这条记录，UPDATE 是当前读，能看到并更新到它**；更新之后这条记录的 trx_id 变成了 A 自己的，A 再普通 SELECT 就能看到它了——**这就是 RR 下的幻读**。关键不是 Read View 中途变了，而是 **UPDATE 用的是当前读，而且事务始终能看到自己的修改**。
>
> ---
>
> **日志**这块，InnoDB 和 Server 层的分工：
>
> | 日志          | 层级          | 内容                                     | 作用                                                         |
> | ------------- | ------------- | ---------------------------------------- | ------------------------------------------------------------ |
> | **redo log**  | InnoDB 引擎层 | **物理日志**，记录某个数据页做了什么修改 | **崩溃恢复**（持久性 D）。环形文件，靠 checkpoint 推进       |
> | **undo log**  | InnoDB 引擎层 | **逻辑日志**，记录逆向操作               | **事务回滚**（原子性 A）+ **MVCC 版本链的数据来源**          |
> | **binlog**    | **Server 层** | **逻辑日志**，记录变更                   | **主从复制** + **时间点恢复** + 逻辑备份 + 订阅变更（Canal） |
> | **relay log** | 从库          | 中转站                                   | 从库 IO 线程拷来的 binlog 先落地再回放                       |
>
> 一句话记：**redo log 解决 durability，binlog 解决 replication。**
>
> **为什么 redo 和 binlog 需要两阶段提交？** 因为它们在不同层：redo 是 InnoDB 的，binlog 是 Server 的。如果 redo 写完了、binlog 还没写就宕机，重启后 redo 说"这个事务已提交"，但 binlog 里没有，主库有数据从库没有，**主从永久不一致**。所以用两阶段提交：**写 redo（prepare）→ 写 binlog → 写 redo（commit）**。宕机在 prepare 之后、binlog 之前，binlog 里没有对应记录，就判定为未提交、回滚；宕机在 binlog 之后、commit 之前，binlog 完整，就判定为已提交、提交。**最终以 binlog 是否完整为准。**
>
> ---
>
> 最后补一个实战点：**InnoDB 的行锁是加在索引上的**。如果 UPDATE 的条件没走索引，就会锁住所有扫描到的记录加间隙，**相当于锁表**。所以建索引不只是性能问题，是并发正确性问题。

| 他会追问                                         | 你怎么答                                                     |
| ------------------------------------------------ | ------------------------------------------------------------ |
| **"四种隔离级别分别会出现什么问题？"**           | RU：脏读、不可重复读、幻读全有。RC：脏读没了，不可重复读和幻读有。**RR（InnoDB 默认）：不可重复读没有，幻读在普通快照读里也没有，但在当前读场景下需要靠 Next-Key Lock 来防**。Serializable：全没有，但普通 SELECT 会变成隐式加锁的锁定读。 |
| **"RC 和 RR 的 Read View 创建时机有什么区别？"** | **RC 每条普通 SELECT 都新建一个 Read View**，所以能看到别的新提交的数据 → 不可重复读；**RR 只在第一次快照读时创建，之后一直复用**（锁定读不复用这个快照）→ 可重复读。 |
| **"redo log 什么时候刷盘？"**                    | `innodb_flush_log_at_trx_commit`：**0** 每秒刷，MySQL 崩溃丢 1 秒；**1** 每次提交都刷盘（默认，最安全）；**2** 每次提交写到 OS 缓存、每秒刷盘，MySQL 崩溃不丢、OS 崩溃丢 1 秒。 |

| **"undo log 什么时候删除？"**                    | **不是事务一提交就删**。更新或删除产生的 undo 要等**不再被任何旧快照使用**之后，由后台的 purge 线程清理。undo 页本身也受 redo 保护。 |
| **"间隙锁和临键锁的区别？"**                     | Record Lock 锁索引上的**具体记录**；Gap Lock 锁索引记录**之间的间隙**，防止插入；**Next-Key Lock = Record + Gap**，这是 InnoDB 默认的行锁粒度，用来防幻读。 |
| **"binlog 有哪几种格式？"**                      | **statement**（记 SQL）、**row**（记行的 before/after 镜像）、**mixed**。默认是 row。**statement 格式在主从复制中不安全**——触发器、UUID()、NOW() 这类不确定性函数会导致主从不一致，这也是触发器在主从场景要小心的根源之一。 |

1. **别说"MVCC 是把数据复制一份"** —— 是**隐藏字段 + undo 版本链 + Read View**。
2. **别把 `max_trx_id` 说成"m_ids 里的最大值"** —— 它是**下一个要分配的事务 ID**。
3. **别说"RR 彻底解决了幻读"** —— 要说清楚是**当前读 + Next-Key Lock** 在防，而且给 UPDATE 那个例子。

### Q16 MySQL 触发器：before/after 的区别；trigger 能保证幂等性吗

> 触发器是**和表关联的数据库对象**，在 INSERT、UPDATE、DELETE 前后自动执行一段 SQL，属于数据库层的逻辑。
>
> ---
>
> **before 和 after 的核心区别**是：
>
> **before 是"改数据"，after 是"看结果做事"。**
>
> 具体四点：
>
> **① before 里可以修改 NEW 的值**，改了之后会影响实际写入的数据。所以它适合做**校验、拦截、归一化、填默认值**。而 **after 里 NEW 和 OLD 只能读**，改了也没用。
>
> **② before 拿不到自增 ID**，因为 INSERT 的时候自增 ID 还没生成；**after 可以拿到**。
>
> **③ after 能看到最终结果**，适合做**审计、写历史表、级联更新、推消息**。
>
> 举个例子：before 触发器里检查 URL 格式，不合法就直接 `SIGNAL SQLSTATE '45000'` 把插入拒掉；after 触发器里把这条记录写进审计表。
>
> 版本上：MySQL 5.7 每个事件只能有**一个 before 加一个 after**；**MySQL 8.0 支持多个触发器**，可以用 `FOLLOWS` 或 `PRECEDES` 指定顺序。另外触发器里**不能再查询或修改触发它的表**，会报 1442 错误。
>
> ---
>
> **关于幂等性，答案是：触发器本身不能保证幂等性。**
>
> 幂等的意思是同一个操作执行一次和执行多次，最终效果相同。**能不能幂等，取决于触发器体里写的是什么逻辑，触发器只是一个执行机制。**
>
> 最典型的反例是 AFTER UPDATE 里做累加：`UPDATE t SET counter = counter + 1`。同一个 UPDATE 事件触发两次，counter 就加了两次，**这是典型的非幂等**。根本原因是**增量操作天然不幂等**——第一次已经把状态改了，第二次读到的是改过的值。
>
> 要做到幂等，规则是：**用"覆盖"和"条件判定"代替"无条件增量"**。比如把 `counter = counter + 1` 改成 `counter = NEW.total_pv`，用绝对值覆盖，重复执行多少次结果都一样。
>
> 再比如 AFTER INSERT 写审计表，也是非幂等的，要加唯一索引配合 `INSERT IGNORE` 或者 `ON DUPLICATE KEY UPDATE`，让**数据库层面做原子幂等判定**，重复触发时第二次被唯一索引挡住，没有副作用。
>
> BEFORE 里如果做的是**基于 NEW 的绝对值计算**，比如 trim 一下、格式化手机号、把状态归一化，那它天然是幂等的；但如果写的是 `SET NEW.x = NEW.x + 1`，一样不幂等。
>
> ---
>
> 所以我的结论是三层：**第一，触发器不提供幂等性，它只是把逻辑下沉到了数据库，任何应用层调用都绕不过去；第二，要幂等必须用覆盖、条件判定、唯一索引约束，去替代无条件的累加和插入；第三，最可靠的幂等方案是"业务唯一键加唯一索引"，因为那是数据库层面的原子判定，不依赖应用层逻辑，也不怕并发。**
>
> ---
>
> 顺便说一下我为什么不推荐用触发器做幂等：**触发器是隐式执行的**，代码里看不见，排查起来很痛苦；它**逐行执行**，大表上开销明显；它**影响 binlog**，statement 格式下主从复制不安全；而且**不能跨库**，迁移和备份恢复也麻烦。所以业界更倾向于把幂等逻辑放在应用层，用数据库唯一索引兜底。触发器更适合用在审计、数据归档这类应用层不方便做、但对性能不敏感的场景。

#### 🔍 追问表

| 他会追问                                     | 你怎么答                                                     |
| -------------------------------------------- | ------------------------------------------------------------ |
| **"before 里怎么拒绝一条非法数据？"**        | 用 `SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '错误信息'`。这是 MySQL 5.6+ 引入的标准做法，比以前往某个字段塞一个值然后在外层判断要干净得多。 |
| **"触发器里能不能用 SELECT 查询自己的表？"** | MySQL 5.7+ **不允许**，会报 **1442** 错误（"Can't update table 'xxx' in stored function/trigger because it is already used by statement"）。因为会无限递归。 |

| **"触发器和存储过程怎么选？"**               | 触发器**由事件自动触发，调用方感知不到**，适合审计、同步；存储过程**由应用显式调用**，逻辑更可控、可测试、可版本管理。**幂等、复杂业务逻辑优先放存储过程或应用层，别放触发器。** |

#### ⚠️ 别踩的坑

1. **别说"触发器能保证幂等"** —— 这是本题的核心陷阱。
2. **别说"after 里也能改 NEW"** —— 改了不生效。

#### 🔗 项目关联

> 我项目里的幂等**一处都没有用触发器**，全都是"幂等键加唯一索引"这一套。比如**短链创建**：`t_link` 表上有 `UNIQUE KEY (full_short_url, del_time)`，插入冲突时捕获 `DuplicateKeyException` 抛业务异常——注意这比"应用层先查再插"要可靠，因为后者在并发下有 **TOCTOU 问题**（查的时候不存在，两个线程同时插）。而**同一个 originUrl 要幂等地拿到同一个短链**，我是用 Redisson 分布式锁把创建过程串行化、再在锁内二次校验实现的。RAGent 那边 Redis Stream 的消息消费，用的是 **SETNX 幂等状态机**保证同一条消息只被有效消费一次。所以整个项目里，**触发器一次都没用**——因为幂等这件事，用唯一索引做原子判定比用触发器做条件判断更可靠。

### Q17 Redis 内存淘汰策略

> 先说个前提：Redis 是**单线程执行命令**的，内存满了必须腾地方，靠两个配置——`maxmemory` 设上限，`maxmemory-policy` 选策略。
>
> **要先把两件事分开**：**过期删除策略**处理的是"已经到 TTL 的 key"，Redis 用的是**惰性删除加定期删除**；**内存淘汰策略**处理的是"内存压力"，**哪怕 key 还没过期、甚至根本没设 TTL，也可能被淘汰**。这是两个不同机制。
>
> ---
>
> 淘汰策略一共 8 种，分三类。
>
> **第一类是不淘汰：`noeviction`。** 超过 `maxmemory` 时不主动删数据，**可能继续增加内存的写命令会返回 OOM 错误**，但普通查询和删除还能执行。**这是 Redis 3.0 之后的默认策略**，注意不是 allkeys-lru。
>
> **第二类是在"设置了过期时间"的 key 里淘汰**，这四个是 volatile 开头：
>
> - `volatile-lru`：淘汰 TTL 的 key 里最久未使用的
> - `volatile-lfu`：淘汰最少使用的
> - `volatile-random`：随机淘汰
> - `volatile-ttl`：优先淘汰**剩余 TTL 最短**的，也就是最接近过期的
>
> **第三类是在"所有 key"范围内淘汰**：
>
> - `allkeys-lru`：整个键空间里最久未使用的
> - `allkeys-lfu`：最少使用的
> - `allkeys-random`：随机
>
> ---
>
> **LRU 和 LFU 的区别**：LRU 看的是**最近有没有用过**，LFU 看的是**一段时间内用得多不多**。一个商品一直很热但刚好最近没访问，另一个以前没人看刚被访问一次，LRU 更可能保留后者，LFU 更可能保留前者。
>
> Redis **没有为所有 key 维护一条严格的 LRU 链表**，因为那样每次读写都要维护，代价太高。它用的是**近似 LRU**——随机采样若干个 key（`maxmemory-samples`，默认 5），从样本里挑最久未用的，**时间复杂度 O(1)**。
>
> LFU 的经典问题是**历史包袱**：曾经很热的 key 即使现在不热了，频率计数还很高，导致冷数据一直占着位置、真正的新热点进不来。Redis 4.0 引入的 LFU 对计数做了**对数衰减**，让老计数慢慢过期。
>
> ---
>
> **两个坑**要提醒：
>
> **第一，volatile 系列有个致命前提**：如果你的 key **都没有 TTL**，volatile 系列会**一个都淘汰不掉**，最后直接 OOM。所以用 volatile 就必须保证大部分 key 有过期时间。
>
> **第二，Redis 不能淘汰某些 key**：**主从复制中的从节点**不淘汰，避免主从数据不一致。
>
> ---
>
> **怎么选**：
>
> - 纯缓存、key 都可以丢 → `allkeys-lru` 或 `allkeys-lfu`，**但要记得默认是 noeviction，得自己显式配**；
> - Redis 里还放了锁、库存这种不能丢的数据 → **`noeviction`**，宁可不写也不丢，最好**把这类数据拆到独立实例**；
> - TTL 混合、需要精确控制 → `volatile-ttl`。
>
> 最后补一个运维点：**`maxmemory` 不能设成物理内存的全部**，要给操作系统、复制缓冲区、还有持久化时的写时复制（fork）留余量，一般是物理内存的 60% 到 70%，否则 fork 那一刻就会 OOM。

#### 🔍 追问表

| 他会追问                                      | 你怎么答                                                     |
| --------------------------------------------- | ------------------------------------------------------------ |
| **"noeviction 之后会怎样？"**                 | **可能继续增加内存的写命令会返回 OOM 错误**，普通查询和删除通常仍可执行。应用层要处理这个错误。而且 noeviction **不等于关闭过期删除**，已经过期的 key 仍然会按过期策略被清掉。 |
| **"volatile-lru 淘汰的 key 还没到 TTL 啊？"** | 对。**内存淘汰是按内存压力来的，不管 TTL**。volatile-ttl 优先淘汰的是**剩余存活时间最短**的（最接近过期的），但它同样**不要求已经过期**。这是内存淘汰和过期删除的本质区别。 |
| **"maxmemory 是进程实际占用的上限吗？"**      | **不是**。`maxmemory` 限制的是**参与淘汰判断的内存量**，进程 RSS 还包括复制缓冲区、客户端输出缓冲、内存碎片这些开销。 |
| **"内存碎片率怎么看？"**                      | `mem_fragmentation_ratio` = RSS / used_memory。**大于 1.5 且内存占用较大时**，说明碎片明显，可以开启 `activedefrag` 自动整理。 |
| **"Redis 里有大 key 怎么办？"**               | 大 key 会占大量内存、拖慢操作、阻塞主线程（比如用 DEL 删大集合会阻塞）、撑爆网络带宽、还会拖慢主从同步。治理手段：**用 `UNLINK` 代替 `DEL`**（异步释放）、**拆成多个小 key**、用 `SCAN` 代替 `KEYS`、给集合类操作加 limit。 |

#### ⚠️ 别踩的坑

1. **别说"默认是 allkeys-lru"** —— **默认是 `noeviction`**（Redis 3.0 之后），这是高频错点。
2. **别把"过期删除"和"内存淘汰"混为一谈** —— 他如果追问"区别是什么"，能答上来就是加分项。

#### 🔗 项目关联

> 我项目里的 Redis 用法直接决定了这个选型。我用 Redis 存了**短链跳转缓存**（有 TTL，按有效期设置）、**UV/UIP 统计集合**（TTL 180 天）、**分布式锁**、还有**幂等状态机**。**分布式锁和幂等状态机是绝对不能被淘汰的**——锁被淘汰会导致两个线程同时进临界区，幂等标记被淘汰会导致消息重复消费。所以严格说，**我这个架构下应该用 `noeviction`，或者把锁和幂等状态拆到独立的 Redis 实例**。这是我回头看设计时意识到的一个隐患，只是我当前是纯缓存用途，配置成 allkeys-lru 还没暴露问题。另外 `tryInit(1e8, 0.001)` 那个布隆过滤器也是存在 Redis 里的，**它要是被淘汰了，整个防穿透的第一道防线就失效了** —— 所以它同样应该是不参与淘汰的数据。

#### 2. 每题留一个"钩子"给面试官追问

说完主干之后，主动**停在半空**，让他有东西可问：

- Q7 → "……这也是为什么 JDK8 用了 `ForwardingNode`。"
- Q11 → "……这也是我项目里刻意避免嵌套加锁的原因。"
- Q15 → "……这里有个细节是 ReadView 的 max_trx_id 不是 m_ids 的最大值。"

**别一次讲完所有细节**，你不主动给钩子，他可能就换个话题了。

#### 3. 不会的时候的三种兜底话术

| 情况                   | 话术                                                         |
| ---------------------- | ------------------------------------------------------------ |
| **完全不会**           | "这块我确实没有深入了解过。我的理解是……（说你能推理出的部分），但具体实现我记不太清了。如果这块重要，我能回去补。" |
| **知道结论不知道原理** | "结论我知道是 XXX，底层实现我记得是走 XXX，但具体细节我不敢乱说，怕讲错。" |
| **记混了两个概念**     | "这里我需要想一下……（停顿 3 秒）……应该是 A 和 B 两者，区别在于……（说完后主动补）不过这块我记忆不是特别确定。" |

> **绝对不要硬编。** 面试官听到"我不知道"和听到一段明显背错的东西，前者还能救，后者直接判死刑。你上一场就吃了"硬撑"的亏。
