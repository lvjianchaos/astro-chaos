3. 说有一个很大数据量（50w+）的 excel，每行就是一个记录，有些字段可能有问题，并且主键还可能有重复，要你如何做一系列操作去插入 MySQL？（答得不是很好）

   > *面对 50 万行以上 Excel 导入 MySQL、存在脏数据、主键重复的场景，核心思路不是直接读 Excel 逐条 insert，而是「先离线校验清洗 → 分批导入 → 冲突策略控制 → 事后核对 + 日志兜底」，优先保障数据准确性，再保证导入性能，防止数据库雪崩、脏数据入库。*

   首先风险是大数据量容易 OOM、逐条插入性能差、主键冲突中断、脏数据污染正式表。 所以我会采用**流式读取 Excel + 临时中间表**的方案： 
   
   第一，用 SXSSF/openpyxl 流式逐行读取，不加载全表到内存，每行先做代码层面的字段格式校验，校验失败的行写入异常表，记录 Excel 行号和错误信息，不中断任务；校验通过的数据按 1000 左右一批，用 JDBC batch 插入临时表，开启 rewriteBatchedStatements 优化批处理。 
   
   第二，全部进临时表之后，通过 SQL 批量分组排查主键重复，区分合法数据、重复数据、脏数据，避免单行查库带来的 IO 压力。 
   
   第三，按照提前和业务约定的冲突策略：要么重复数据打入异常表人工审核，要么使用 on duplicate key update 做覆盖，分批迁移合法数据到正式业务表，控制批次大小，用小事务，防止锁表和大事务回滚。 
   
   第四，导入完成后生成统计报告，异常数据提供导出，支持断点续传、批次隔离，导入放在业务低峰期，必要时临时去掉二级索引提速；
   
   如果只是一次性简单导入，也可以使用 load data infile，但是校验和异常处理弱，业务平台化导入优先代码流式 + 临时表方案。
   
   > **openpyxl 是 Python 中功能全面的 Excel 文件编辑器，适合需要精细控制样式的常规报表；SXSSF 则是 Apache POI（Java）为百万级海量数据导出而设计的低内存流式写入器，以牺牲随机访问换取内存稳定性**。

#### 完整步骤

##### Step1：前置准备

1. 建临时表  `t_import_tmp`，结构和正式业务表尽量一致；

   字段类型、长度、约束和正式表对齐，但是临时表先不设置主键唯一约束，防止导入中途直接中断；额外增加几个辅助字段：
   
   - `import_id`：本次导入批次号（用来区分每一次导入任务，多批次导入隔离）
   - `row_no`：Excel 原始行号（出问题可以直接定位到 Excel 哪一行，非常重要）
   - `check_result`：校验状态（0 待校验、1 合法、2 字段非法、3 主键重复）
   - `err_msg`：错误信息（保存失败原因：手机号超长、日期格式错误、重复主键等）
   
2. 确认数据库参数：调整`rewriteBatchedStatements=true`（JDBC 批处理必须开，MySQL 才会真正合并多条），调大`max_allowed_packet`，防止单行数据过大报错；**关闭业务高峰导入，选低峰期**。

3. 定义好【冲突策略】：

   - 策略 A：保留旧数据，新来的重复记录直接丢弃，标记为重复；
   - 策略 B：新数据覆盖旧数据（`ON DUPLICATE KEY UPDATE`）；
   - 策略 C：重复数据全部落去重复异常表，人工审核后处理；

> 重点：**策略必须业务先行，不能自己默认覆盖或者丢弃**。

##### Step2：流式读取 Excel + 单行列级校验（内存中逐行校验，早发现脏数据）

流式一行一行读，**不一次性加载全部 Excel 到内存**，每一行做基础校验：

1. 基础格式校验：字段非空校验、数字 / 日期格式、字符串长度、枚举值、去除前后空格、清洗换行特殊字符；
2. 校验失败：不立刻中断任务，写入**异常记录表 t_import_error**，记录行号、原始内容、错误原因，继续跑下一行；
3. 校验通过：放到批处理缓冲区，攒一批（比如 1000/2000 条，不要太大，太大 batch 容易报错），执行 batch 插入临时表。

> 为什么不一次性 50w 一个 batch？batch 过大容易事务日志暴涨、锁、数据包超限，一般 500~2000 条一批是工业常用值，可以做成可配置。

##### Step3：全部写入临时表之后，MySQL 层批量校验、识别主键重复

全部导入 tmp 表之后，用 SQL 做批量校验，比代码循环查库快得多：

1. 先找出重复主键：

```sql
SELECT pk_col,COUNT(*) FROM t_import_tmp WHERE import_id='批次号' GROUP BY pk_col HAVING COUNT(*) >1;
```

1. 更新临时表的 check_result、err_msg，标记重复行；
2. 分离三类数据：
   - ✅ 干净合法无重复数据；
   - ⚠️ 主键重复数据；
   - ❌ 字段脏数据（前面代码校验漏掉的数据库层非法数据）。

> 这里对比一个坑：不要**读取一行就 select 数据库查主键是否重复**！50w 次 select，DB 直接打满，IO 爆炸。

##### Step4：数据迁移到正式业务表（根据预先约定的冲突策略）

方案 1（推荐，可控）：先把干净无重复的数据 insert 到正式表；重复的数据分流到异常表，通知运营人工核对。 

方案 2（业务允许覆盖）：使用 `INSERT ... ON DUPLICATE KEY UPDATE` 语法，从临时表往正式表迁移，数据库层面原子处理主键冲突。

> 注意：on duplicate key 适合主键 / 唯一索引冲突场景，大批量的时候也要分批，不要一次性 50w 行跑一个超大 SQL，防止锁表、事务回滚日志过大。

##### Step5：统计、日志、产出报告

导入完成后，统计指标：总行数、成功行数、脏数据行数、主键重复行数；生成导入报告； 

所有异常数据（脏行、重复行）持久化保存，导出给业务方核对修正 Excel，支持重试导入； 

日志里记录批次号、耗时、异常明细，方便排查。

##### Step6：兜底 & 重试机制

1. 支持断点续传：记录已经处理到 Excel 的行号，如果中途程序宕机，下次导入可以从该行继续，不用从头重新导入 50w；
2. 事务设计：**每一个 batch 单独小事务，而不是 50w 行一个大事务**。如果大事务一旦失败，全部回滚，前面导入的全部作废，耗时巨大；小 batch 失败只回滚当前这一批；
3. 限流：导入的时候控制写入 QPS，避免和正常业务争抢数据库连接、CPU；
4. 备份：重要数据导入前，对正式表做备份。
